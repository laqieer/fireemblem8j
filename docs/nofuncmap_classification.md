# No-funcmap US-C-portable functions: region-same vs region-different

_Generated by `scripts/classify_nofuncmap.py`. Do not edit by hand._

**The question (D41/D51/D52 follow-up).** The honest matching-C ceiling is
~8332 US-C-portable functions (US `src/<tu>.o` text symbols);
3669 are graduated. The ungraduated remainder splits by whether
the funcmap (`layout/us_jp_funcmap.tsv`, the exact/masked tiers from
`match_us_jp.py`) tracks each function. The **no-funcmap** functions were never
run through those tiers -- but no-funcmap is **NOT** region-different:
**2191 ALREADY-graduated** US-C functions were no-funcmap too
(whole-TU / verified-run ports cover funcmap and non-funcmap alike). So the
no-funcmap pool is an **unmeasured MIX**. This report measures it.

## Methodology -- why a raw-byte search is wrong, and the sound classifier

`match_us_jp.py`'s exact/masked search looks for a function's RAW US bytes in the
JP ROM, masking only pointer-literal words. A region-same function RELOCATED to a
different JP address has different bytes at every relocation site -- `bl`/pc-rel
`ldr` offset fields and the trailing constant pool, not just pointer literals --
so a raw search misses almost all relocated region-same code. **Validated:** run
against the known-region-same control (the graduated no-funcmap functions), the
raw-byte search labels ~97% of them "region-different" (false). That is exactly
why most US-C functions are no-funcmap: relocated, not different.

The sound classifier is the project's own `find_runs.py` (D2) test, applied per
function: **compile** the US source in isolation (`extract_run.py` + agbcc), read
the **true relocation offsets** from `objdump -r`, **mask** every reloc-affected
byte, and masked-search the JP ROM. Verdicts: `region-same-unique` (masked .text
uniquely located in JP), `region-same-ambiguous` (>=2 JP sites; resolves when
carved with a neighbour), `region-different` (adequate needle, zero JP match ->
genuine codegen difference), `inconclusive` (needle too short / isolated compile
needs TU context). On the known-region-same control the reloc-aware test labels
~97.5% region-same with **0** false region-different, so its region-same count is
a sound LOWER bound and region-different a sound UPPER bound on the hand-decomp
frontier.

### Full-pool result (exact) + inconclusive projection

- **region-same = 1953 CONFIRMED** (46.8% of decided) -- **the
  lever's remaining pool** (harvest_verified_runs / graduate_shared_run /
  bind_tu_data / subrun_decompose; the binding+carve machinery from D41-D53).
  Every one is listed in `layout/nofuncmap_region_same.tsv`.
- **region-different = 2224 CONFIRMED** (53.2% of decided) -- the
  genuine permuter / hand-decomp (IDA/Ghidra) frontier.
- **inconclusive = 300** (short needle / isolated compile needs TU context).
  Splitting these at the decided rate projects ~140 more
  region-same and ~160 more region-different, i.e. a
  whole-pool estimate of **~2093 region-same / ~2384
  region-different**.

Implication for the ceiling: combined with the
3669 already-graduated and the 186 funcmap-tracked
ungraduated (also region-same), the byte/relocation-confirmable matching-C reach
is ~5948 / 8332 (~71% of
the ceiling), leaving ~2384 no-funcmap functions as the real
region-different hand-decomp frontier.

> Caveat: `region-same` here means the JP instruction stream matches the US one
> modulo relocation -- it is the LEVER's domain (carve + data-binding, D41-D53),
> not a promise each lands in `make compare` without the per-TU binding work the
> waves describe. Some unique-masked-match functions still need their TU-private
> data bound first (e.g. the D45/D51 UnpackRaw class). They remain lever pool,
> not hand-decomp.
